## 是不是云端模型的问题

不是。分两点：

**1. 两个教师一致给出的标签是可靠的。** 评审方让两个子 agent 盲标了 160 条：教师判为 none 的文档和 MCP 描述各 60 条，教师判为 request 的 40 条。
- 教师一致的 none：两人分别认同 119/120 和 120/120，而且这些文本全部是纯参考内容，比如 API 签名、示例代码、更新日志、“查看某区域 DNS 设置”这类工具能力说明。
- 模型在这类文本上误报 23%。这是“合成数据训练、真实文本测试”的领域差距：训练集几乎全是云端模型写的短篇合成文档，模型从未见过 reST 标记、API 参考、真实的工具描述 JSON。

**2. 教师之间的分歧暴露了定义问题。** 在全部候选上，两个教师对文档片段只有 56% 一致：
- DeepSeek 把 517/1,255 判为 request，MiMo 只判 121/1,255；
- 分歧几乎都在“要安装，运行 pip install …”“克隆、提交、推 PR”这类通用操作步骤上。

评审方复核的 40 条 request 中，没有一条是“现在就对某个具体对象做某件事”，全部是通用步骤或工具自身的用法约束。D′ 评审定下的“合法的写给人的操作说明也算 request”，在真实文档上无法稳定执行，这是评审方的定义问题。

另外，训练数据的生成和复核主要依赖 DeepSeek，它对 request 的理解偏宽，模型也继承了这一点。

## 为什么金标准和保留集都过了

金标准片段来自我们自己构造的评测场景，保留集是另一个云端模型写的合成文本，本质上都还是“干净的短文档”。真实良性集是第一次接触真实世界的文本。这也说明当初坚持加这道门槛是对的。

## 定义修订（设计文档 §4.2）

request 收窄为**具体任务**：要求当前读者现在执行一个带具体对象（文件、URL、命令、其他工具、凭据）的操作。

下列三类归为 none，并用 `kind` 字段记录：
- 通用操作步骤；
- 只约束工具自身调用方式的用法说明；
- 纯参考内容。

例外：要求对该工具或该文档以外的资源采取行动的，仍算 request，这是工具投毒的典型形态。真实注入几乎都带具体目标，所以收窄定义不会漏掉它们；具体目标是否敏感、是否越权，仍由规则层和 A1/A2 判断。
