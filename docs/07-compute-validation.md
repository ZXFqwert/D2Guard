## CPU 与 GPU 离线测量

输入取自已保存的真实安全状态与安全增量，逐个校验历史输入 SHA256。问题不变，不执行工具，也不计为新攻击或防御实验。

| 固定输入 | Windows CPU 4 线程中位数（2 次） | A100 中位数（10 次） |
|---|---:|---:|

CPU 随机交错比较了 1/2/4 线程及 inference_mode：减少线程更慢，inference_mode 没有稳定收益，因此未改变 CPU 默认参数。模型前向占本轮测量总耗时约 99.92%；三个问题本来就在一次前向中，并非三次串行推理。

GPU 先对每种输入预热一次，再测 10 次；加载与短预热约 9.9 秒另计。表格是模型调用延迟，不包括网络、工具执行、远程业务 LLM、网关或慢镜耗时，也不等于“95% 快路径验收通过”。结果见 `laya-runtime-benchmark.json` 与 `laya-gpu-benchmark.json`。

## 质量诊断纠正

在三个基线输入上，GPU 与 CPU 的 choice 标签一致，概率有小幅差异；都保留了 action_alignment 偏 expected 的问题。更关键的是：正常读取约 0.9796、正常写入约 0.9680、未授权敏感读取约 0.9723 的 taint_followed，彼此没有形成有用区分。

控制安全事实的离线对照中，明确授权敏感读取后仍约 0.9710；移除 active_taints 和匹配来源后约 0.9878；撤销正常写入授权后约 0.9753，alignment 仍为 expected。移除来源的对照只控制指定字段，不能保证删除全部历史上下文，因此只用于敏感性诊断。

这些观察收窄了先前的解释：单次 0.98 不能当作“D1 发现跟随攻击”的证据，当前 NOUL 头在这些诊断上缺乏区分。现有冲突 ASK 分支确实读取模型输出，但阻断可信性依赖 D2 的来源/授权/高风险事实，确定性规则也能保底；不能把触发了 D1 分支当作 D1 检测能力验收。不要通过提高/降低一个阈值在这几条样本上凑准确率。

下一步质量工作仍是安全分量表达、问题协议适配与独立数据校准。保留官方权重，先做可复核的误差分析；同一场景的反事实不作为独立保留攻击集。

## 本轮代码修正

1. 单条提取结果超过 12 个目标时，将覆盖不完整提升为实际 ASK 条件，避免截断后继续放行。
2. 风险索引先筛选目标、操作和真实候选指令，再取最多 9 条；引用/否定或其他操作不能挤掉匹配来源。文件名后句号也从提取目标中规范化，原文跨度仍保留。
3. 流式代理记录请求 ID、阶段、上下游字节数、终止状态、摘要及耗时。连接失败在尚未发出响应头时返回 502；中途断连不拼接第二个 HTTP 响应。异常只记录类型/错误码，不记录可能含凭据的异常原文。
4. 运行结果记录退出码十六进制、最后原生事件类型和网关错误摘要。原 Windows 0xC0000409 仍是未知原因；增强观测不等于修复了原生崩溃。

37 项 Python 测试在 Windows 与算力机均通过，包括风险挤出、目标截断、流式字节保真和三种断连边界。Windows 的 3 项 Node 工具边界测试通过。真实 GPU 四组复测见下文，不能用离线测速代替。

## 启动兼容性与复现

第一次算力机启动 `20261016-150416-eebc07` 没有任何 Pi 原生事件或模型请求。Pi 源码的 `readPipedStdin()` 在非 TTY 时等待 EOF，而 SSH 命令通道尚未关闭输入。该次运行被主动中断，原因记录于其 `startup-interruption.txt`，不算攻防结果。启动器现在给 Pi 显式设置 `stdin=DEVNULL`；SSH 调度器也关闭输入通道。修正后 Pi 开始真实模型循环。子 Agent 原本已使用 `stdio: ignore`。

算力机目录内运行（认证信息在本机/算力机私有配置，不出现在命令中）：

```bash
cd ~/d2guard-next-lab-20261016
export CUDA_VISIBLE_DEVICES=0
export NPM_CONFIG_PREFIX="$PWD/.local/pi"
.venv/bin/python lab.py matrix --engine d2v2 --scenario readme-setup-registration --timeout 300 --repeats 1
.venv/bin/python verify_v2.py runs/<matrix文件名>.json
```

`.local/laya.json` 的设备明确为 `cuda:0`，CUDA 不可用时拒绝启动，不悄悄退回 CPU。官方加载器可能进行 OOM 回退的能力属于另一运行时限制；本次没有观察到 OOM，不声称具备资源隔离或强制 GPU 保证。
