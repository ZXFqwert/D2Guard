# 12 · D²Guard Codex 执行方案

> 依据：`docs/整体设计文档.md`（v2，下称“设计文档”）、`docs/11-claude-review.md`、`AGENTS.md`。
> 用法：**每次只交给 Codex 一个阶段。** 阶段结束后它必须停下汇报，由人确认验收后再开下一阶段。每个阶段的启动话术见文末。

---

## 全局工作规则（每个阶段都适用）

1. 开工前先读设计文档中与本阶段相关的章节和 `AGENTS.md`。如果发现设计与代码冲突，先汇报再动手，不要自行改设计。
2. 所有模型行为必须来自 Pi 真实的 LLM 循环。不回放、不伪造、不按测试环境改变行为；失败原样保留。
3. 不能把规则产生的结果写成“Laya 检出”。每个 ASK/BLOCK 都必须记录 `rule_id`、风险等级和证据引用。
4. 不靠调阈值、加关键词来适配某一条攻击。阈值只能在验证集上确定，保留集不参与任何调参。
5. 密钥只放在 `.local/` 或进程环境变量里；实验只用合成凭据；日志、提交、场景资源中不得出现上游密钥。
6. 每个阶段结束时，在 `docs/03-status.md` 追加一段：改了什么、测试结果、真实运行 ID、未解决的问题。设计文档 §12 状态表中对应行的状态也要更新。
7. 单元测试、真实运行证据和离线诊断三类结果分开报告，不能混算。
8. 阶段内遇到阻塞（环境、权限、上游 API）时，记录下来并停下，不要绕过约束。
9. 开工前先读上一阶段的评审 `docs/reviews/stage-<上一阶段>-review.md`；其中“转入下一阶段”的条目属于本阶段任务，同样要逐条自检。
10. 阶段开始时先把上一阶段已验收的改动提交为一个 Git 检查点（提交信息写明阶段与运行批次），不得混入本阶段改动；提交前统一换行符，避免整文件重写式 diff。

## 阶段评审循环

每个阶段按同一循环推进，直到阶段 I：

1. **Codex 执行**：只做当前阶段，结束时写阶段报告（`docs/<编号>-stage-<x>-report.md`）、追加 `03-status.md`、更新设计文档 §12，然后停下。
2. **Claude 评审**：读阶段报告、实际代码改动和真实运行的裁决记录；重跑单元测试；针对边界情况写探针用例。评审结论只有三种：**通过**、**有条件通过**（非阻断问题转入下一阶段）、**退回**（列出必须返工的项，Codex 返工后重新评审）。
3. **Claude 更新文档**：写 `docs/reviews/stage-<x>-review.md`；需要改设计的，改设计文档并在对应小节写修订记录；更新本文件的阶段状态表和下一阶段任务；同步到 claude.ai 项目。
4. **Claude 给出下一阶段提示词**，由人确认后交给 Codex。
