## 1. 哪个更可靠

对于“当前实现具备什么、哪里缺失、哪些数据可以对外陈述、接下来先做什么”，04–06 的工程审查依据目前更充分。反重力方案在项目线索、旗舰案例构思和展示叙事方面有价值，但多处把设计建议写成既有事实，把目标数字写成实测，把检测启发式写成形式化保证。未经修正，不适合直接转为作品报告的技术承诺。

这不是按作者身份判定。应逐条看证据：官方要求看原文，现有功能看代码和实跑，借鉴项目看固定源码，性能看原始逐例数据，安全效果看独立副作用观测。两份报告都不能证明“一定过初赛”或“达到一等奖”。

我上一轮遗漏 MCP Context Protector 和 Pipelock，反重力对此的补充值得吸收。Pipelock 的实际工程能力甚至比其报告的概括更扎实：已存在独立边界的签名回执。我的“统一出站、许可和回执”建议也必须继续对照既有项目，不能靠模块名字宣称原创。04–06 当前仍以静态分析为主，没有完成运行时验证，也不是穷尽全球相关项目的综述。

## 4. 两个新项目，真正值得借什么

### MCP Context Protector

审查快照：Trail of Bits，`05e56c1616f4382ca25eb15bdfc98c4967bbdd74`，源码版本 0.1.0，Apache-2.0。[官方发布说明](https://blog.trailofbits.com/2025/07/28/we-built-the-security-layer-mcp-always-needed/)及以下源码可复核。

有价值的是发现阶段的 TOFU 审批、逐工具隐藏、定义变更后重新批准、真实 MCP 转发、工具响应 quarantine 与人工释放。它补上了我们上一轮对“工具还没调用，描述已经进入模型”的强调不足。

### Pipelock 与 LLM Guard

Pipelock 快照：`fb1611d4ef55965f4ecbd5d180f6a6032b1fae28`。所读核心文件 Apache-2.0；它的企业目录和付费发行能力应分别核清许可。LLM Guard 快照：`168c1034ffdb33837e7ae6fd6a16b80567c1be03`，MIT，官方仓库已归档；模型权重和依赖许可另外核对。

最值得吸收的是已知 Canary 的多视图扫描、有预算的解码、高熵辅助信号以及边界外 Ed25519 回执/离线验证。它们是现有工程，不是本队原创。[Canary scanner](https://github.com/luckyPipewrench/pipelock/blob/fb1611d4ef55965f4ecbd5d180f6a6032b1fae28/internal/scanner/canary.go#L88)、[body 熵处理](https://github.com/luckyPipewrench/pipelock/blob/fb1611d4ef55965f4ecbd5d180f6a6032b1fae28/internal/contententropy/contententropy.go#L35)、[receipt](https://github.com/luckyPipewrench/pipelock/blob/fb1611d4ef55965f4ecbd5d180f6a6032b1fae28/internal/receipt/receipt.go#L47)。

这些机制只观察经过中介的流量。代理可被绕过时，收据不能证明没有其他外发。公钥必须外部可信；只有记录自带公钥仅证明自洽。签名证明签过一份记录，不自动证明操作员诚实、记录完整或实际接收结果。独立 sink 与执行结果观测仍然必要。

LLM Guard 的 [Secrets](https://github.com/protectai/llm-guard/blob/168c1034ffdb33837e7ae6fd6a16b80567c1be03/llm_guard/input_scanners/secrets.py#L414)使用模式/高熵插件，PromptInjection 是文本分类，Sensitive 是 PII 输出检测；均需要应用正确消费结果。它们不能自动提供执行许可、会话秘密台账或跨 Agent 来源传播。

## 5. 新《07》执行方案仍需修正

07 吸收了评测常量、独立接收端、ASK 和慢镜出站问题，这个调整有价值。但不能把文档内分工视为已经授权或启动的代码修改，本轮仍只审查。以下内容尚不宜照写照做：

1. C2 写“子线程接收器”不构成进程独立的观测边界；应至少单独进程，记录原始请求并由评测方读取。先证明正常请求能实际到达，才解释攻击时的 0 bytes；连接错误不能混算为防御成功。
2. C5 应先原子地验证并消费单次授权，再执行，避免“执行后销毁”期间的并发重放。令牌需要绑定主体、会话、工具身份、规范化参数、期限及必要的策略版本；失败/重试语义需明定。
3. A1 改为“配置自修改越权机制靶场”，除非已取得原产品受影响版本的实际复现证据。只需隔离靶场的无害标记文件等副作用即可证明越权，不需要把真实反弹 Shell 当展示门槛。
4. A2 中标签包裹不能叫“隔离沙箱”；工具描述清洗不能等于投毒彻底切断。A3 中“0.1ms”“硬件级熔断”“彻底杜绝”没有当前实现和实测依据。
5. A4 应叫“已知秘密和异常外发检测增强”，不能把熵和变异字典直接命名为完整 IFC。随机 Canary 只植入独立靶场副本，需同时保留其位置和生成记录。
6. A5 应展示“来源区间、已知变换、对应参数与裁决”；推断的模型影响须明确标识。匿名规则须核对比赛原文，不能把“一切代码注释绝对不得有作者”当作已核实统一要求；第三方许可的版权/NOTICE 也不能随意删除。
7. “全局零硬编码”应改成“指标、实测结论和运行证据不伪造”。固定测试 fixture、场景标签、枚举、策略常量本来就允许存在；删除一切常量不是合理验收标准。

## 6. 推荐的合并顺序与验收

**P0：可信度与执行边界。** 修评测输入链、展示常量、独立副作用观测；补宿主隔离、秘密模型出站约束和会话状态隔离。每个数字必须追到逐例记录和公式。暂不能从静态审查推导 ASR、时延或奖项等级。

**P1：一条完整旗舰链。** 真实 Agent 读取攻击输入，经真实 MCP 或子 Agent 产生动作；调用前权限检查；必要时单次 ASK；独立 sink/文件系统观测结果；导出来源和裁决证据。同时跑正常任务，证明安全没有靠禁用全部工具取得。

**P2：有边界的高级机制与展示。** 接入 TOFU、完整工具身份/定义绑定、明确授权契约与可验证回执；把编码检测、高熵、来源约束各自的贡献通过消融拆开。再采用反重力三幕叙事、正确 ATLAS 分类和来源高亮，所有现场时延取当次实际测量。

可对外陈述的贡献必须落到具体实现和对照结果：跨 MCP/子 Agent 的权限是否会放大，所有模型与工具出口是否受同一秘密约束，回执是否能与实际执行对应，来源图哪些边是事实、变换或推断。IFC、TOFU、权限契约、签名日志和 SOC 可视化都有既有工作；组合价值需要实证，不能用“业界首个”替代检索和验证。
